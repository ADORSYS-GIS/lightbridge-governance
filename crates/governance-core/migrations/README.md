# Migrations

Generated by `cratestack migrate diff` from `../schema/governance.cstack`
(ADR-0009). There is no hand-written migration here, and adding one is not a
shortcut anyone gets to take — see the ADR.

`postgres/schema.snapshot.json` is what `migrate diff` compares the schema
against. Applying migrations does not read it; only generating a new one does.

## ⚠️ Read this before regenerating the snapshot

The snapshot is `format_version: 1`. cratestack 0.7.10 writes and expects v2
(`projections` instead of `schema`, cratestack/cratestack#205), and **refuses**
to read v1:

```
Error: reading snapshot at migrations/postgres/schema.snapshot.json
Caused by: failed to parse snapshot file ...: missing field `projections`
```

That is the safe failure — it stops rather than diffing against an empty schema
and emitting `CREATE TABLE` for tables that already exist. Applying migrations
is entirely unaffected, and was verified against both a clone of the live
database (no-op, no checksum complaint) and an empty one (all five apply, giving
a schema byte-identical to the one 0.5.1 built).

So nothing is broken today. **The next schema change is what needs this
resolved**, and the obvious fix is a trap.

### The obvious fix destroys data

`cratestack migrate baseline` introspects a live database and writes a v2
snapshot from it. Run it against this schema and the very next `migrate diff`
wants to emit — verified, in a throwaway copy:

```sql
DROP INDEX copilot_org_dailys_natural_key;      -- and 7 more
DROP TABLE model_pricing;
CREATE TABLE model_pricings (...);
```

Both are **real drift**, not an introspection artifact — confirmed against the
live database, not inferred:

| | Live database (what the migrations built) | What the schema projects to |
|---|---|---|
| pricing table | `model_pricing` | `model_pricings` |
| composite unique indexes | `<table>_natural_key` | `<table>_<col>_<col>_..._key` |

The short index names were a deliberate hand-edit to the generated SQL — the
reason is written down in `postgres/20260802000939_init/up.sql:119`. The
singular `model_pricing` is the same class of divergence. Neither was ever
recorded in the snapshot, because a v1 snapshot stored the *authored schema*
rather than live reality, so schema-vs-snapshot compared clean and the drift
stayed invisible. 0.7.10's introspection is the first thing that has ever
looked at the actual database and compared.

Dropping those eight indexes would remove the unique constraints that
`ON CONFLICT` resolves against — which is to say it would silently take out the
idempotency guarantee the whole collector rests on ("reprocessing a day must not
change row counts"). `DROP TABLE model_pricing` takes the pricing history with
it.

`migrate diff` refuses to write any of this without `--allow-destructive`, so
the guard rail holds. **Do not reach for that flag to get past the error.**

### What to actually do

Pick one deliberately; this is a maintainer's call, not a default:

1. **Reconcile the schema to the database** — add the mapping attributes
   (`@@map`, named `@@unique`) so the projection produces `model_pricing` and
   `<table>_natural_key`. Then baseline, and diff comes out empty. Keeps the
   database untouched; makes the schema tell the truth.
2. **Reconcile the database to the schema** — a real rename migration
   (`ALTER TABLE ... RENAME`, `ALTER INDEX ... RENAME`), never a drop/create.
   More churn on a live system, and the index rename must not leave a window
   with no unique constraint.

Either way, prove it: regenerate, run `migrate diff` again, and confirm it
reports nothing to do.

### Also worth knowing

`migrate baseline`'s drift report claimed `applications_tenant_id_fkey` "is
declared in the schema but does not exist in the live database". It does exist
— `SELECT conname FROM pg_constraint WHERE contype='f'` lists it, along with
the other eight. Treat that report as advisory and check each finding against
the database before acting on it.
